## In-window data path: Metabase 0.63.19

One clean instance of the `metabase/metabase:v0.63.19` image with this JAR as
the only file in `plugins/`, embedded application database, temporary port. A
real MaxCompute project was added over the REST API and deleted by the same run.

| Check | Result |
| --- | --- |
| Driver registered by the running instance | Pass (`Registered driver :maxcompute (parents: [:sql-jdbc])`) |
| Create the real MaxCompute database | Pass, HTTP 200 |
| Native `SELECT 1 AS e2e_value` | Pass, one row `[1]` |
| Full schema and field sync | Not completed here — see below |
| MBQL against a synced table | Not attempted (needs the sync cell above) |
| Real `ARRAY` column without `TO_JSON` | Not re-run on 0.63.19; the same minor's 0.63.18 cell is in `v0.1.1-metabase-supported-window.md` |

Metabase registers a plugin driver lazily, on first use, so a startup-log grep
taken too early reports nothing. A separate pitfall worth writing down: Metabase
refuses a `plugins/` directory it cannot write to, falls back to a temporary one,
and the only visible symptom is `value must be a valid database engine` when the
database is created.

Full schema sync against the shared test project was attempted three times for
this artifact on 0.63.18 (two 1,800 s windows and one solo 4,500 s window) and
did not complete; the project holds tens of thousands of tables. A longer
timeout is not evidence, so `full_schema_sync_e2e` and `mbql_query_e2e` stay
`not_verified` and 0.1.1 stays `verification-pending`.

So 0.64.0-beta shows no break at the interface this driver uses. At the time it
was written this was still not a reason to widen anything: the beta is a
pre-release, the window is expressed in stable minors, and no 0.64 build had a
data-path cell. **Correction on 2026-11-01**: 0.64 went GA on 2026-10-07
and 0.64.4 shipped on 2026-10-30, so "0.64 has none yet" is no longer true.
The 0.64.x window is now verified on its own line against the current GA patch;
until that lands, this release's window still ends at `<0.64.0`. It is recorded as a boundary candidate with `decision: excluded`. 0.64 has since
gone GA (0.64.1 on 2026-10-07, 0.64.4 on 2026-10-30), so the "when the first
stable patch ships" plan in this paragraph is being executed on its own
verification line against the current GA patch; the next driver release moves the
build baseline into whichever window that lands on, instead of stretching 0.1.1
across it.

## Correction on 2026-11-11: the MBQL failure recorded on 2026-11-08 was the gate, not the artifact

The full-gate row above first read `mbql_query: fail` for Metabase 0.63.22, and
the same claim went into `known_failures`. Both are retracted.

Measured per table on 2026-11-10 against the same published artifact and the same
image, **16 of 18** synced tables answer MBQL on 0.63.22. The double-qualified
table name is emitted there too, but 0.63.x also emits the column reference in the
matching shape, so the server resolves it. Every question fails only from
Metabase **0.64** on (`0` of 18 on 0.64.4 and on 0.65.2, `ODPS-0130071`), which is
outside the window this matrix declares. The two tables that do not answer on
either side fail for their own reasons, and the fixed cell names them - a view
whose base table was deleted (`ODPS-0130071`, HTTP 400), and a table holding a
Long value below -2^63 (HTTP 500, `InvalidData: Bigint out of range`) - so they
are not evidence about qualification.

Where the false reading came from, since it is worth not repeating: the
repository's own gate reads every candidate with `curl -fsS` inside a command
substitution under `set -euo pipefail` (`scripts/run-real-e2e.sh:3`, `:310-337`),
so the first table answering HTTP 400 ends the whole cell, and its success test
requires exactly one row (line 330), which the five completed-empty candidates in
this project can never satisfy. One early abort was taken for a project-level
verdict.

The sentence this file carried until 2026-11-13 - that the success test "cannot
read the asynchronous `202 [ASYNC: completed]` response this Metabase line
returns" - was itself false, and it was written before anything had read a 202
body. Measured with the fixed cell on 0.51.14, 0.63.22 and 0.64.4, every answered
table returns HTTP 202 whose body is already terminal (`status: "completed"`,
`data.rows` present). Why the shipped cell went green on 0.51.14 and died on
0.63.22 over the same artifact and project: on 0.51.14 a failing candidate arrives
as HTTP 202 with the failure inside the body, so `curl -f` never saw an error; on
0.63.22 the same failure arrives as HTTP 400. Metabase moved query errors from the
body into the status code between those lines; the driver and the project did not
change. A patch to the cell is under review in the driver's build repository, not
merged; until it lands, the script in this directory reproduces the row that
produced no verdict rather than the decided ones.

Unchanged by this correction: plugin load, database creation, native `SELECT 1`
and full schema sync (18 tables / 42 fields, 20.8 s) are directly observed.

| `v0.63.22`, shipped cell | no verdict | 1 of 18 | - | - | - | - | aborts with `curl: (22) … 400` after `Native query passed`, no table named, no evidence file written |
| `v0.63.22`, fixed cell | **pass** | 18 | 16 | 11 | 5 | 2 | 17x 202, 1x 400, 1x 500 |

| `v0.64.4`, fixed cell, locally built fix candidate | pass, observation only | 18 | 16 | 11 | 5 | 2 | 17x 202, 1x 400, 1x 500 |

Read as cells, not as a story: in-window `0.63.22` **passes** MBQL with the released
artifact; `0.64.4` **fails** every question, which is the defect the fix under

still has no reading: schema sync at large-project scale, and MBQL on a genuinely
schema-enabled project - a 2026-11-13 attempt against this project with
`MAXCOMPUTE_NAMESPACE_SCHEMA=true` stopped in the sync step with the server saying

fail. Two claims inside the 2026-11-11 correction on this page are retracted above;
the 2026-11-08 `fail` row was already retracted, and the row stays in
`compatibility.yaml` as the aborted attempt it actually was.
