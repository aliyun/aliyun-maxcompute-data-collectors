## In-window data path: Metabase 0.63.19

One clean instance of the `metabase/metabase:v0.63.19` image with this JAR as
the only file in `plugins/`, embedded application database, temporary port. A
real MaxCompute project was added over the REST API and deleted by the same run.

| Check | Result |
| --- | --- |
| Driver registered by the running instance | Pass (`Registered driver :maxcompute (parents: [:sql-jdbc])`) |
| Create the real MaxCompute database | Pass, HTTP 200 |
| Native `SELECT 1 AS e2e_value` | Pass, one row `[1]` |
| Full schema and field sync | Not completed here — see below |
| MBQL against a synced table | Not attempted (needs the sync cell above) |
| Real `ARRAY` column without `TO_JSON` | Not re-run on 0.63.19; the same minor's 0.63.18 cell is in `v0.1.1-metabase-supported-window.md` |

Metabase registers a plugin driver lazily, on first use, so a startup-log grep
taken too early reports nothing. A separate pitfall worth writing down: Metabase
refuses a `plugins/` directory it cannot write to, falls back to a temporary one,
and the only visible symptom is `value must be a valid database engine` when the
database is created.

Full schema sync against the shared test project was attempted three times for
this artifact on 0.63.18 (two 1,800 s windows and one solo 4,500 s window) and
did not complete; the project holds tens of thousands of tables. A longer
timeout is not evidence, so `full_schema_sync_e2e` and `mbql_query_e2e` stay
`not_verified` and 0.1.1 stays `verification-pending`.

## 0.64.0-beta: loads, and still stays outside the window

The driver's dependency surface was enumerated from source — required
namespaces plus every `defmethod` target and every var it resolves at runtime —
and each symbol was required/resolved inside the exact image:

| Metabase | Symbols resolved | Driver in `available-drivers` |
| --- | --- | --- |
| 0.52.17 | `metabase.driver-api.core/*` does not exist yet and `metabase.models.secret/get-secret-string` is gone — the recorded 0.52.x–0.55.x database-creation failure, re-confirmed at API level | Yes |
| 0.63.19 | 4 fallback names absent, preferred API present | Yes |
| 0.64.0-beta | **identical to 0.63.19 across all 48 symbols** | Yes |

So 0.64.0-beta shows no break at the interface this driver uses. It is still not
added to the supported window: it is a pre-release, the window is expressed in
stable minors and 0.64 has none yet, and nothing above 0.63.19 has a data-path
cell. It is recorded as a boundary candidate with `decision: excluded`. When the
first stable 0.64 patch ships, it gets this load smoke plus the data-path
checks, and the next driver release moves the build baseline into that window
instead of stretching 0.1.1 across it.

## Reproduce

```bash
# one cell, against the published bytes
DRIVER_JAR=/path/to/maxcompute-metabase-driver-0.1.1.jar \
  METABASE_IMAGE=metabase/metabase:v0.63.19 ./scripts/run-load-smoke-image.sh

# the 48-symbol dependency surface inside any pinned image
docker run --rm --entrypoint java \
  -v "$DRIVER_JAR:/tmp/driver.jar:ro" -v ./probe.clj:/tmp/probe.clj:ro \
  metabase/metabase:v0.64.0-beta \
  -cp "/app/metabase.jar:/tmp/driver.jar" clojure.main /tmp/probe.clj
```
